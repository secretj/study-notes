## 01. 한 줄 답

Go 코드는 OS 스레드를 직접 만지지 않아요. 우리는 고루틴만 만들고, 그 고루틴을 실제 스레드에 올려서 돌리는 건 Go 런타임이 알아서 해요.

그래서 코드는 평범하게 순서대로(동기식으로) 짜는데, DB 응답을 기다리는 동안 스레드가 노는 일은 런타임이 알아서 막아 줘요.

> 💡 코드는 동기식으로 짜는데, 돌아가는 건 비동기처럼 돌아가요. 이게 Go의 제일 큰 매력이에요.

> 📌 스프링 MVC (톰캣)\
> **요청 하나 = 스레드 하나**\
> 응답이 나갈 때까지 스레드 하나를 붙잡고 있어요. 톰캣 기본 최대 스레드는 200개예요.

> 📌 Go net/http\
> **요청 하나 = 고루틴 하나**\
> 연결이 들어오면 고루틴이 알아서 생겨요. 스레드 풀 설정 같은 건 없어요.

> 📌 스프링 + 가상 스레드\
> **Go랑 거의 같은 방식**\
> Java 21의 가상 스레드는 고루틴이랑 비슷한 개념이에요. Spring Boot 3.2부터 설정 한 줄로 켤 수 있어요.

## 02. 식당으로 비유하면

- **스프링(톰캣)** — 손님 한 테이블에 직원 한 명이 전담으로 붙어요. 손님이 메뉴 고민하는 동안에도 직원은 옆에 서서 기다려요. 직원이 200명이면 201번째 손님은 입구에서 기다려야 해요.
- **Go** — 직원 몇 명이 여러 테이블을 돌아다녀요. 손님이 고민 중이면 그 테이블은 잠깐 두고 다른 테이블 주문을 받으러 가요. 손님이 "주문할게요" 하면 아무나 한가한 직원이 와서 받아요.

여기서 테이블이 고루틴, 직원이 OS 스레드예요. 직원 수는 적어도 테이블은 수천 개를 감당할 수 있어요.

## 03. G, M, P — 고루틴 스케줄러의 세 가지

Go 런타임 스케줄러를 설명할 때 꼭 나오는 게 G, M, P예요.

- **G (고루틴)** — 실행할 일 하나예요. `go f()` 하면 G가 하나 생겨요. 처음엔 2KB 정도로 아주 작게 시작하고 필요하면 런타임이 키워 줘요.
- **M (Machine)** — 진짜 OS 스레드예요. 실제로 일하는 직원이에요.
- **P (Processor)** — 논리 프로세서예요. 직원(M)이 일하려면 꼭 하나 잡고 있어야 하는 작업대 같은 거예요. P마다 자기 대기열(로컬 큐)이 있어요. P 개수는 `GOMAXPROCS` 이고, 기본값은 CPU 코어 수예요.

> 🖼️ **그림으로 보면** — 스레드(M)는 P를 잡아야 고루틴을 돌릴 수 있어요. DB 응답을 기다리는 고루틴은 옆으로 빠지고, 스레드는 쉬지 않고 다음 고루틴을 돌려요.

1. **P 개수** — `GOMAXPROCS` 만큼 있어요. 기본은 CPU 코어 수예요
2. **실행** — 스레드(M)가 P를 잡고, P의 로컬 큐에서 고루틴을 하나씩 꺼내 돌려요
3. **작업 훔치기** — 할 일이 떨어진 P는 놀지 않고 다른 P의 고루틴을 가져와요
4. **기다리기** — 응답을 기다리는 고루틴은 네트워크 폴러로 빠지고, 스레드는 다음 고루틴을 돌려요

## 04. 기다려야 할 때 런타임이 하는 일

고루틴이 멈추는 상황은 크게 세 가지예요. 어떤 경우든 다른 고루틴은 멈추지 않고 계속 돌아가요.

#### 1. DB 쿼리, HTTP 호출처럼 네트워크를 기다릴 때

런타임이 그 고루틴을 네트워크 폴러에 맡겨 두고, 스레드는 바로 다음 고루틴을 돌려요. 응답이 오면 고루틴이 다시 대기열에 들어가요.

#### 2. 파일 읽기처럼 시스템 콜에서 오래 멈출 때

이때는 스레드도 같이 멈춰요. 대신 런타임이 P를 다른 스레드에 넘겨서, 나머지 고루틴은 계속 돌아가게 해요.

#### 3. 계산만 계속하면서 CPU를 안 놔줄 때

Go 1.14부터는 런타임이 강제로 끊고 다른 고루틴한테 차례를 넘겨요. 그 전에는 무한 루프 하나가 스레드를 계속 붙잡을 수 있었어요.

## 05. 스프링(톰캣)은 어떻게 처리할까

스프링 MVC는 톰캣 스레드 풀 위에서 돌아가요. 요청이 들어오면 스레드 하나가 붙고, 응답이 나갈 때까지 그 스레드는 다른 일을 못 해요. DB 응답을 기다리는 동안에도요.

- **스레드 개수 제한** — 톰캣 기본 최대 스레드는 200개예요(`server.tomcat.threads.max`). 200개가 다 바쁘면 나머지 요청은 줄 서서 기다려요.
- **스레드 하나가 무거워요** — OS 스레드는 설정에 따라 0.5~2MB 정도 메모리를 써요. 그래서 수만 개로 늘리기 어려워요.
- **자주 겪는 장애** — 느린 외부 API 하나 때문에 스레드 200개가 다 붙잡히면, 그 API랑 상관없는 요청까지 전부 멈춰요.

### 가상 스레드를 켜면

```yaml
# application.yml (Spring Boot 3.2+, Java 21+)
spring:
  threads:
    virtual:
      enabled: true
```

이러면 톰캣이 요청마다 가상 스레드를 만들어요. JVM이 가상 스레드 여러 개를 진짜 스레드 몇 개에 돌려 가며 태워요. Go 고루틴이랑 거의 같은 방식이에요.

### 그런데 함정이 있어요: 제한이 없어지면 DB가 터져요

카카오페이 기술블로그에서 실제로 겪은 일이에요. 톰캣 스레드가 200개로 막혀 있을 때는 그 제한이 자연스럽게 브레이크(Back Pressure) 역할을 해서 DB 커넥션 풀이 버텼어요. 가상 스레드로 바꾸니 요청을 제한 없이 다 받아 버려서, 결국 DB 커넥션을 못 빌리고 타임아웃이 났어요.

**Go도 똑같아요.** 고루틴은 제한 없이 생기니까, 병목은 DB 커넥션 풀로 옮겨 가요. 그래서 Go에서는 `db.SetMaxOpenConns()` 로 DB 연결 수를 정하고, 필요하면 동시에 처리할 요청 수를 따로 제한해 줘야 해요.

## 06. 한눈에 비교

`좋다` 는 그냥 쓰면 되는 것, `보통` 은 신경 좀 써야 하는 것, `나쁘다` 는 구조적으로 손해 보는 거예요.

| 궁금한 것 | 스프링 MVC | Go | 스프링 + 가상 스레드 | 참고 |
|---|---|---|---|---|
| 요청은 누가 처리해? | OS 스레드 | 고루틴 | 가상 스레드 | 03장, 05장 |
| 하나당 메모리는? | **나쁘다** 0.5~2MB | **좋다** 2KB부터 시작 | **좋다** 몇 KB | 페이히어 글 |
| 요청이 몰리면? | **나쁘다** 200개 넘으면 줄 서요 | **좋다** 다 받아요 | **좋다** 다 받아요 | 다 받으면 DB가 병목 (05장) |
| DB 응답 기다리는 동안 스레드는? | **나쁘다** 그냥 붙잡고 있어요 | **좋다** 다른 일 하러 가요 | **보통** 다른 일 하러 가요. 단 `synchronized` 안에서는 묶여요(pinning) | JDK 24에서 개선 |
| 요청 정보를 알아서 넘겨줘? | **좋다** ThreadLocal이 알아서 | **보통** `ctx` 를 직접 넘겨야 해요 | **좋다** ThreadLocal 그대로 돼요 | 07장 |

## 07. Go로 넘어가면 제일 먼저 부딪히는 것: ThreadLocal이 없어요

스프링에서 `@Transactional`, `SecurityContextHolder`, 로그 MDC는 다 ThreadLocal로 돌아가요. "지금 이 스레드가 처리 중인 요청"에 정보를 몰래 붙여 두는 방식이라, 우리는 신경 안 써도 알아서 넘어갔어요.

Go에는 이런 게 없어요. 트랜잭션, 로그인한 사용자, 타임아웃, 취소 신호를 전부 `ctx` 와 함수 인자로 직접 넘겨야 해요. Go 함수 첫 번째 인자가 거의 항상 `ctx context.Context` 인 이유가 이거예요.

```java
// 스프링: 트랜잭션이 ThreadLocal에 숨어 있어요
@Transactional
public void archive(long mailId) {
    mailRepo.markArchived(mailId);   // 알아서 같은 트랜잭션을 써요
    auditRepo.write(mailId);
}
```

```go
// Go: 트랜잭션(tx)이랑 ctx를 직접 넘겨요
func (s *Service) Archive(ctx context.Context, mailID int64) error {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback() // Commit 되면 아무 일도 안 해요

    if err := s.mailRepo.MarkArchived(ctx, tx, mailID); err != nil {
        return err
    }
    if err := s.auditRepo.Write(ctx, tx, mailID); err != nil {
        return err
    }
    return tx.Commit()
}
```

| 조심할 것 | 왜 문제가 되는데? | 어떻게 해? |
|---|---|---|
| **코드가 길어져요** | 어노테이션 하나면 되던 걸 함수마다 손으로 넘겨야 해요 | 트랜잭션 시작과 끝은 서비스 한 곳에서만 하고, 리포지토리는 tx를 받기만 해요 |
| **ctx를 중간에 새로 만들어요** | 중간에 `context.Background()` 를 새로 만들면 타임아웃이랑 취소 신호가 거기서 끊겨요 | 핸들러에서 받은 `r.Context()` 를 끝까지 그대로 넘겨요 |
| **ctx에 이것저것 넣고 싶어져요** | `context.WithValue` 로 트랜잭션까지 넣으면 ThreadLocal처럼 숨은 의존성이 다시 생겨요 | 요청 ID처럼 진짜 요청 범위 값만 넣고, 나머지는 인자로 넘겨요 |
| **동시 실행이 너무 쉬워요** | `go f()` 한 줄로 동시 실행이 생기니까 같은 변수를 동시에 건드리기 쉬워요 | CI에서 `go test -race` 를 돌려요 |

<details>
<summary>답 보기</summary>

핸들러가 끝나는 순간 `r.Context()` 가 취소돼요. 그 ctx로 DB 조회나 SMTP 호출을 하면 `context canceled` 에러가 나면서 메일이 안 나가요. 응답 뒤에도 계속해야 하는 일은 `context.WithoutCancel(r.Context())` (Go 1.21+)로 취소만 끊고 타임아웃은 따로 걸어요. 서버가 재시작될 때 같이 날아가지 않게 하려면 큐로 넘기는 게 제일 안전해요.
