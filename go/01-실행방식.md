# 01. Go 서버는 데몬을 띄워야 돌아갈까?

> 작성: 2026-11-03 · 태그: Go

**Go 학습 · 01**

PHP만 하다가 Go를 보면 "이거 데몬으로 계속 띄워 놔야 하는 거야?"라는 생각이 먼저 들어요. 결론부터 말하면, 따로 띄울 건 없고 Go 프로그램 자기 자신이 데몬처럼 계속 떠 있는 거예요. 이 페이지는 그 차이를 PHP-FPM과 비교해서 정리해요.

## 01. 한 줄 답: 따로 띄울 건 없어요

Java는 JVM이, PHP는 PHP 인터프리터가 있어야 코드가 돌아가요. Go는 `go build` 하면 실행 파일 하나가 나오고, 그 파일만 있으면 바로 실행돼요. 따로 깔아 두거나 띄워 둘 프로그램이 없어요.

계속 떠 있느냐는 그 프로그램이 무슨 일을 하느냐에 달려 있어요.

> 💡 Go 서버는 "뭔가를 띄워 놔야 돌아가는" 게 아니라, 자기 자신이 계속 떠 있는 프로그램이에요.

> 📌 CLI 도구, 배치\
> **할 일 하고 끝나요**\
> 실행하고, 작업하고, 종료돼요. go-mailtools 같은 도구가 이런 식이에요.

> 📌 API 서버\
> **계속 떠 있어요**\
> `http.ListenAndServe()` 가 요청을 기다리는 동안 프로그램이 안 꺼져요. 데몬처럼 보이는 이유가 이거예요.

> 📌 서버리스 (Lambda 등)\
> **플랫폼이 알아서**\
> 요청이 오면 플랫폼이 띄우고, 한가해지면 알아서 내려요.

## 02. PHP-FPM이랑 비교하면

사실 PHP도 계속 떠 있는 게 있어요. 바로 php-fpm이에요. php-fpm 자체가 데몬이에요. 그러니까 "Go만 데몬이 필요하다"가 아니라, **둘 다 뭔가는 계속 떠 있고 떠 있는 게 다를 뿐**이에요.

- **PHP** — php-fpm(PHP 실행기)이 계속 떠 있어요. 우리가 짠 코드(.php 파일)는 요청이 올 때마다 읽어서 실행하고, 요청이 끝나면 다 버려요.
- **Go** — 우리가 짠 코드가 들어 있는 실행 파일이 통째로 계속 떠 있어요. 요청이 끝나도 메모리에 그대로 남아 있어요.

> 🖼️ **그림으로 보면** — PHP는 요청마다 코드를 실행하고 버리고, Go는 코드가 곧 서버라서 계속 살아 있어요.

| 궁금한 것 | PHP (php-fpm) | Go |
|---|---|---|
| 계속 떠 있는 건? | php-fpm과 워커 프로세스들 | 우리 코드가 들어간 실행 파일 하나 |
| 요청이 끝나면? | 전역 변수까지 싹 초기화돼요 | 전역 변수, 캐시, DB 커넥션 풀이 그대로 남아요 |
| 누가 계속 살려 둬? | php-fpm이 스스로 데몬으로 떠 있어요 | systemd, Docker, k8s 같은 관리 도구가 띄우고 지켜봐요 |

참고로 PHP 쪽에서도 "요청마다 다 버리는 게 아깝다"는 이유로 Swoole, RoadRunner, FrankenPHP처럼 PHP 코드를 계속 띄워 두는 방식이 나왔어요. FrankenPHP는 Go로 만든 웹서버(Caddy) 안에 PHP를 넣은 구조예요.

## 03. 그럼 데몬이랑 뭐가 달라?

거의 같아요. 데몬은 "사용자가 직접 건드리지 않아도 백그라운드에서 계속 일하는 프로그램"이에요. 계속 떠 있는 Go 서버도 딱 그거예요.

차이는 **누가 백그라운드로 보내느냐**예요. 옛날 데몬은 프로그램이 스스로 백그라운드로 숨었어요. 요즘 Go 서버는 그냥 앞에서(포그라운드) 실행되고, 백그라운드로 돌리는 일은 systemd가 대신 해 줘요.

### 옛날 데몬이 스스로 하던 일

#### 1. 자식 프로세스를 만들고 자기는 죽어요 (fork)

흔히 "fork off and die"라고 불러요. 부모가 사라진 자식은 init(systemd)이 데려가요.

#### 2. 터미널과 연결을 끊어요 (setsid)

그래서 터미널을 닫아도 같이 죽지 않아요.

#### 3. 입출력을 정리하고 백그라운드에서 계속 돌아요

화면에 찍던 출력을 `/dev/null` 이나 로그 파일로 돌려요.

### 요즘 Go 서버는 이렇게 띄워요

서비스 파일 하나만 만들면 돼요. `Restart=always` 를 넣으면 죽었을 때 systemd가 다시 살려 줘요.

```ini
# /etc/systemd/system/myapi.service
[Unit]
Description=my api

[Service]
ExecStart=/opt/myapi/myapi
Restart=always

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload      # 서비스 파일 다시 읽기
sudo systemctl enable --now myapi # 부팅 때 자동 실행 + 지금 바로 실행
systemctl status myapi            # 잘 떠 있는지 확인
journalctl -u myapi -f            # 로그 보기
```

| 궁금한 것 | 옛날 데몬 (예전 nginx, sshd) | 요즘 Go 서버 + systemd |
|---|---|---|
| 백그라운드로는 누가 보내? | 프로그램이 직접 fork 해요 | systemd가 대신 해요 |
| 로그는? | 프로그램이 파일에 직접 써요 | 그냥 화면(stdout)에 찍으면 systemd가 모아요 |
| 죽으면? | 따로 감시 스크립트가 있어야 해요 | `Restart=always` 한 줄이면 돼요 |
| SSH로 들어가서 `./myapi` 로 직접 실행하면? | 알아서 백그라운드로 가요 | 터미널 닫으면 같이 꺼져요. 그래서 systemd에 맡기는 거예요 |

## 04. Go는 왜 스스로 데몬이 안 될까

Go 프로그램은 시작하자마자 스케줄러나 GC 때문에 내부적으로 스레드를 여러 개 만들어요. 그런데 `fork()` 는 호출한 스레드 딱 하나만 복사해요. 그래서 fork 하고 나면 자식 프로세스 쪽 Go 런타임이 반쯤 망가진 상태가 돼요.

그래서 Go 표준 라이브러리에는 fork만 따로 하는 함수가 없어요. Go로 데몬을 만들어 주는 라이브러리들은 "자기 실행 파일을 새로 한 번 더 실행"하는 꼼수를 써요.

> 💡 Go 서버는 스스로 데몬이 되려고 애쓰지 않아요. 그냥 앞에서 실행되게 만들고, 띄우고 살리는 건 systemd나 Docker에 맡기는 게 정석이에요.

## 05. 배포할 때 달라지는 점

gw-member dev70은 서버에서 `git checkout` 하고 fpm reload 하면 배포가 끝나요. PHP는 요청이 올 때마다 파일을 새로 읽으니까 가능한 방식이에요.

Go는 이게 안 돼요. 떠 있는 프로그램은 이미 빌드된 코드를 메모리에 들고 있어서, 소스를 바꿔도 아무 일도 안 일어나요.

#### 1. 다시 빌드해요

소스가 바뀌면 `go build` 로 실행 파일을 새로 만들어요.

#### 2. 다시 띄워요

`systemctl restart myapi` 처럼 새 실행 파일로 프로그램을 다시 띄워요.

#### 3. 처리 중인 요청은 마저 끝내고 내려요 (graceful shutdown)

그냥 죽이면 처리 중이던 요청이 끊겨요. 그래서 종료 신호를 받으면 `http.Server.Shutdown` 으로 새 요청은 안 받고, 하던 요청은 끝낸 다음 꺼지게 만들어요. gin 공식 문서에도 예제가 있어요.

### 조심할 것

| 조심할 것 | 왜 문제가 되는데? | 어떻게 해? |
|---|---|---|
| **뭔가가 계속 쌓여요** | PHP는 요청이 끝나면 다 날아가서 몰랐던 문제들(전역 변수 꼬임, 안 끝나는 고루틴, 동시에 같은 변수 건드리기)이 서버가 떠 있는 내내 쌓여요 | 전역 변수를 최소로 쓰고, `go test -race` 로 동시 접근 문제를 잡아요 |
| **배포 방식이 바뀌어요** | 지금처럼 git checkout만으로는 반영이 안 돼요 | 빌드해서 실행 파일을 배포하고, graceful shutdown을 처음부터 넣어요 |

## 06. 스스로 확인해 보기

#### 1. PHP에서 하던 대로 요청마다 "DB 연결 → 쿼리 → 연결 끊기"를 Go 핸들러에 넣으면 무슨 일이 생길까?

<details>
<summary>답 보기</summary>

요청마다 연결을 새로 맺느라 느려지고, 요청이 몰리면 DB 최대 연결 수를 넘겨 버려요. Go에서는 서버가 뜰 때 `sql.Open()` 을 딱 한 번 하고, 그걸 핸들러들이 같이 써요. `*sql.DB` 가 그 자체로 커넥션 풀이거든요.

</details>

#### 2. systemd로 띄운 Go 서버가 로그를 `/var/log/myapi.log` 에 직접 쓰면 뭐가 불편할까?

<details>
<summary>답 보기</summary>

로그 파일이 커지는 걸(로테이션) 직접 관리해야 해요. `journalctl` 이나 Docker 로그로 볼 수도 없어요. 나중에 컨테이너로 옮기면 경로랑 권한도 다시 맞춰야 해요. 그냥 stdout에 찍는 게 제일 편해요.

</details>
